CRITICAL core/scheduler.py:52-53 1.3 _auto_run() bare except 静默吞掉所有错误

问题: _auto_run() 包裹所有定时抓取任务，但用 except Exception: pass 静默处理：

def _auto_run(task_name, fetch_fn, *args, **kwargs):
    try:
        fetch_fn(*args, **kwargs)
        # ... update status to "done"
    except Exception:
        pass  # ← 所有抓取错误被静默吞掉

后果: 数据抓取失败时（API 挂了、网络断了、解析错误），前端看到 fetch_state.status = "done"（因为 pass 不改状态），实际上数据是空的。运维完全无感知。

修复: except Exception as e: logger.exception("[auto_run] %s failed", task_name)，同时把 fetch_state["status"] 改为 "error"，记录 fetch_state["error"] = str(e)。

HIGH fetcher/cycle_signal.py:786-799 4.1 _compute_target_date_str() 不处理周末/节假日 
def _compute_target_date_str() -> str:
    now = datetime.now()
    if now.hour >= 18:
        return now.strftime("%Y%m%d")     # ← 周六 18:00 返回周六！
    yesterday = now - timedelta(days=1)
    return yesterday.strftime("%Y%m%d")   # ← 周日 10:00 返回周六！

周六 18:00 触发 full refresh，target_date = 周六，但 akshare 没有周六数据，step1 会失败。周日 10:00 target = 周六，同样问题。

修复: 用交易日历找最近交易日。或简单判断 now.weekday() >= 5 时回退到周五。
HIGH agent/orchestrator.py:83-98 4.2 _find_claude() 找不到时返回不存在的路径

Line 98: return str(Path.home() / ".nvm/versions/node/v20.20.2/bin/claude") — 这是个 fallback 兜底，但如果文件不存在，_run_skill() 会 Popen 一个不存在的可执行文件，报错信息是 rc=non-zero 而不是"claude not found"，极难排查。

修复: 所有路径都走完后，raise FileNotFoundError("claude CLI not found")。在 _run_skill() 入口加 Path(claude_bin).exists() 检查。

MEDIUM agent/query.py:307-321 4.4 _stale_minutes() 只尝试 3 种时间格式，不支持带时区的 ISO 8601

尝试格式：%Y-%m-%d %H:%M:%S, %Y-%m-%dT%H:%M:%S, %Y-%m-%d %H:%M。如果时间戳是 2026-08-14T07:32:53+08:00（带时区），三种都 ValueError，函数返回 None，stale 检查静默跳过。

修复: 用 datetime.fromisoformat(ts_str)（Python 3.7+ 原生支持 ISO 8601），或 dateutil.parser.parse。
MEDIUM core/scheduler.py 4.5 并发任务共享 FetchStatus 无隔离

max_instances=4 允许同一 job 4 个并发实例。但 _auto_run() 共用 fetch_state dict，并发写入会导致状态覆盖。两个抓取任务同时跑，后完成的会覆盖先完成的状态。

fetch_lock 保护了 dict 写操作，但不保护"读-判断-写"竞态：两个任务都看到 status="idle"，都开始跑，状态被来回覆盖。

建议: 每个 task 用独立的 state key（fetch_state[task_name]），或用 max_instances=1 + coalesce=True 避免同 job 并发。
MEDIUM agent/review_v2.py:498-501 4.6 QUANT_DATA_ROOT 检查位置过晚

QUANT_DATA_ROOT 检查在缓存检查之后（line 500），但 _exodia_latest_stock_date() 在 line 496 就可能需要它（间接依赖 Exodia 数据目录）。如果 QUANT_DATA_ROOT 未设，_exodia_latest_stock_date() 用 fallback 路径可能返回错误日期。

修复: 把 QUANT_DATA_ROOT 检查移到 run() 函数最开头。
LOW fetcher/wecom_notifier.py:378-396 4.7 send_ai_report 并发调用无企微限流保护

企微 webhook 限制 20 条/分钟。send_ai_report 内段间 sleep 0.3s，但如果报告分段 >20 条，或多个 pipeline 同时推送，会触发限流。

目前 0.3s × N 的间隔在单 pipeline 下是安全的（最多 10 段 = 3s），但多 pipeline 并发时无全局计数器。

建议: 加一个全局 threading.Semaphore 或 token bucket 限流器，限制每分钟最多 18 条（留 2 条余量）。
LOW agent/orchestrator.py:120-137 4.8 _kill_proc_group 杀进程后 wait 只等 10s

_kill_proc_group() 发 SIGKILL 后 _wait_wallclock(proc, 10)。SIGKILL 不可被忽略，进程应立即退出。但如果 claude 进程有大量子进程（MCP servers），SIGKILL 传递到整个进程组可能有延迟。10s 超时后 except Exception: pass，proc 可能变成 zombie。

建议: 超时后 proc.wait(timeout=0) 检查是否已退出，未退出则 os.waitpid(os.getpgid(proc.pid), os.WNOHANG) 清理 zombie。
